# One loop for targeted exploration (design for review, 10-24)

Evan 10-24: "we need to rethink our architecture for targeted exploration and make better use of planning and bandit arm
selection tools; we have too many separate routes all carefully hand crafted."  And: "Bad docs that lead to naturally
producing bad patterns are also a problem ... We want to not have to repeat 'do x not y' a bunch."  Goal of this plan:
one architecture in which the right way is the only easy way, with much less code and much less documentation.

Status: plan only.  Nothing is deleted or built yet.  Builds on `../allocator/DESIGN.md` (10-20, which this replaces);
the plugin-side list is in the plugin repo (`ARCH-PLAN.md`).

## 1. Why: what hand-crafted routes cost us (evidence, not taste)

Every campaign this month was a new driver script with its own donor query, budget unit, output path and scoring:
explorer rounds (`chain.py`, `lib_round`), neighbour sweeps, time travel, insertion / removal benches, the row walk and
its stage 2, relax benches, store re-quench passes, target campaigns, overnight shell scripts.  The cost shows up as bugs
that a shared loop would not have had:

* `lib_round`'s "+ best at n + 1" start was never reduced to n: from LIB1 (10-23) to TG1 (10-24) it ran as an n + 1
  packing inside the n explorer.  Nobody noticed because each driver checks only its own outputs.
* 4,291 explorer packings sat outside the store for a day (no sink after jobs); 271 run dirs were found unsunk on 10-24.
* Five separate "pick near-record packings at n" queries (pk/parents, three plugin drivers, the bench) with different
  dedupe tolerances, class filters and holdout rules.
* Budgets in wall minutes in some drivers, CPU in others; an L-walk arm overran its budget 2x because the check was
  between tries.
* Each driver re-implements "results into the store", "keep line-free results below target + tol", "score per arm".
* Wrong conclusions from hand wiring: RS3's "rounded relax as a store move" was a plain re-quench (caught a day later).

And the docs steer toward more of the same: the packer README still names `chain.py -> explore.py` as the production
path and slp2 as "the local minimiser"; `DESIGN.md` routes ideas through `trial.py`, whose tail is marked provisional;
`CLAUDE.md` carries a list of "never X, always Y" rules that exist because the code permits X.

## 2. The architecture in one paragraph

**A goal is data; one scheduler spends CPU on arms; every arm is a stage chain run on donors selected from the store;
every output goes back to the store; reward is measured from the store.**  There are no campaign scripts.  A new idea
is a new stage (or a new parameter of one), never a new pipeline; a new campaign is a new goal file.

## 3. Objects

| object | what it is | where |
|---|---|---|
| **Goal** | targets (a set of n, or "all n"), what counts as progress there, value weights V_n, CPU budget, quantum, pre-registered predictions | `goals/<name>.yaml` (private goals in the plugin repo) |
| **Selector** | a store query: donor n (as an offset from the target), gap window to the frontier, family classes in / out, cluster weighting (α, τ), holdout cutoff | `pk/parents.py` (the one donor query; the five copies go) |
| **Operator** | a stage chain, e.g. `shrink.drop1 \| relax.round.15c.p5`, `grow.add \| relax.round.15c.p5`, `walk(cpu=300)` | `pk/stages.py` registry (stages exist today) |
| **Arm** | (selector, operator, parameter distribution) for one target n | generated by the planner, or listed in the goal |
| **Job** | one arm × a CPU quantum; outputs carry `arm:<goal>/<arm>/<job>` in their sighting source and parent links | `pk/jobs.py` queue (exists) |
| **Store** | the only state between jobs; sink -> converge -> closures on every job's exit | exists (sink, converge built 10-24) |

New stage kinds and operators this needs (small, and each replaces drivers):

* `shrink` (n downward, the mirror of `grow`): `shrink.drop1` (remove one square; candidates on the bounding extremes or
  at the largest local slack), `shrink.lcut` (the inexact L removal of `lcut.py`), `shrink.band` (band deletion).
* `walk(cpu)`: the explorer's local search as one operator: within-n moves (`pk/moves`, today's explorer kinds), quench,
  archive inside the job only; its outputs reach the store like any other stage's.  Its internal kind mix stays fixed:
  the evidence says kind choice moves results by ~1.17x and per-n kind learning hurts at n >= 200 (`analysis/
  bandit_timescale.md`), so the bandit's leverage is in arm choice (donors, operators across n), not kinds.
* Closures as store hooks (Evan 10-24: "the right way to add it as a move"): when a new best or near-record enters at
  n + 1 or at n - 2k - 1, the store queues `shrink.drop1` / exact L-add derived packings at n, then converge.

## 4. The loop

```
plan(goal)      -> arms: for each target n, for each operator family g with its n-offset o
                   (walk 0, add +1, drop -1, L-add +(2k+1), L-cut -(2k+1), compose ...), for each donor family present in
                   the store near the frontier at n - o: one arm.  Prior rate from g's history (hierarchical: g, n-band, n).
allocate        -> Thompson sampling over arms on value per CPU-s, batched with pending-job fantasies (allocator §4).
run(job)        -> donors = selector(store); for each donor: params ~ arm distribution; operator chain; outputs -> sink.
on exit         -> sink -> converge -> closures (jobs.py, built 10-24).
reward(job)     -> from the store delta the job caused: goal progress (below), credited to the job's arm.
report          -> status.py "goals" section: per goal and arm: CPU, reward, posterior, frontier changes, families found.
stop            -> goal budget spent, or the posterior says no arm is worth its quantum (VOI, allocator §4).
```

**Reward = goal progress, measured from the store, never from the driver's own bookkeeping.**  First version (cheap,
countable): new distinct packings at a target n that match the goal (e.g. non-diamond, within +δ of the frontier), each
weighted by 1 / (1 + packings already in its cluster), plus V_n per frontier improvement.  The allocator's potential
Φ (pool value from the parent value model, credit along lineage) is the second version, once the first runs and its
lineage data accumulates.  Both are computed by one function from the store, so every arm is scored the same way.

**Pre-registration lives in the goal file** (predictions per arm family, the metric is fixed by the goal), and the
scheduler refuses to start a goal without it.  The result block is written by the loop at the end (numbers from the
store), and a person adds the reading.

## 5. Example: the 145-150 family (Evan 10-24)

```yaml
goal: fam145-150
targets: [145, 147, 148, 149, 150]
progress: {match: "familymap code not in [G, D, S]", within: 0.02}   # non-diamond, near the frontier
value: {frontier_gain: 1.0, new_match: 0.01}
budget_cpu_h: 15
quantum_cpu_h: 0.5
arms: auto            # planner: walk, add from 146 (donor n-1), drop from near-record non-diamond n+1, L-cut from
                      # 174-176 (n + 2k + 1) then further drops, L-add from row 11
predictions: {any_target_frontier_gain: 0.10, new_matches_at_147_ge_10: 0.5}
baseline: [TG1 147, HB 10-19 147]        # earlier runs whose store rows are the comparison
```

What the planner produces for 147 (illustration): `walk` on 147's own non-diamond pool; `add` from 146's near-record
packings; `drop` from 148 non-diamond donors (none exist within +0.03 today, so this arm starts with a zero-size pool and
gets CPU only once another arm fills 148: the loop does that automatically); `L-cut + drop` from 175 / 176.  Each arm's
outputs become other arms' donors through the store; no routing code.

## 6. What the docs say after this (and what they stop needing to say)

The architecture enforces these, so the rules leave `CLAUDE.md` and the packer docs:

| today's rule (a "do x not y") | enforced by |
|---|---|
| pre-register every test run in PACKER.md | the scheduler refuses a goal without predictions |
| launch compute with jobs.py; report measured CPU | jobs only start through the scheduler; budgets are CPU |
| never copy coordinates; use the store; sink every run | operators read donors from the store and write only through the sink |
| judge a generator by refined outcomes, never raw output | reward is goal progress measured after converge; `walk` is just another arm |
| progress, not clocks | CPU quanta; the posterior decides continuation |
| "do not run X on diamond packings" style advice | selectors carry family filters; arms on diamond donors simply earn little |

The packer docs become three short files: `DESIGN.md` (this architecture, ~200 lines), `CLAIMS.md` (what we learned,
as numbers with evidence; it also seeds arm priors), `README.md` (a ~40-line map: how to write a goal, run it, read the
report).  The lab logs (`PACKER.md`, the plugin `NOTEBOOK.md`) are frozen as history; new runs write their pre-
registration and result into the goal file and a generated result record, not into a growing log.

## 8. Build order (each step leaves a working system; deletion only after its replacement runs)

1. **Lineage yield report** (one query over the store, no compute): per generator / source, how many records and how
   many near-record (+1e-3, +1e-2) packings have it in their ancestry.  Decides which generators get ported.  Tag
   `pre-arch-2026-10`.
2. **Selector + reward + goal spec** (pk/parents as the one donor query; the reward function; goal YAML; status goals
   section).  Check: re-score TG1 and the LW runs from the store with the reward function, and compare with what those
   drivers reported.
3. **Operators**: `shrink.drop1`, `shrink.lcut`, `walk`; closure hooks.  `pk/tests/test_stages.py` covers them.
4. **Scheduler**: arms from the planner, TS on reward per CPU, jobs through the queue, sink attribution by arm.
   First goal: `fam145-150`, pre-registered, with TG1 and the 10-19 147 campaigns as baseline.
5. **Port surviving generators** as stages; delete drivers, experiments and the superseded engine (§7).
6. **Docs**: DESIGN / README / CLAIMS rewrite; freeze logs; trim CLAUDE.md and TODO.md.

Steps 1-4 are about a day of work; step 5 is mechanical but long; step 6 an hour.
