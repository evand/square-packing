## 0. The question

On one and the same finite instance — a finite pose set `P` (cover rows = packing columns) and a
finite family `C` of anchor cliques (cover columns = packing rows, with the point cliques
`K(p,{p})` among them) —

    packing:  max 1.mu   s.t. mu(K) <= 1 for K in C,  mu >= 0    (mu supported on P)
    cover:    min 1.y    s.t. sum_{K in C, S in K} y_K >= 1 for S in P,  y >= 0

are exact LP duals and have the **same value**.  Task G measured a packing-side anchor-clique
gain of `0.104–0.120` at `t = 3.99`; task I measured a cover-side gain of `0.0000, 0.0000,
0.0004` at the `t = 3.98` leaf.  Both cannot be a property of one instance, so the question is
which of *pose set* and *separation depth* accounts for the difference.

**Answer, in one line: the pose set — and the reason is a pricing defect.  Task G's clique LP is
column-starved, because in the `h = 0` (exact-centre) path of `clique_continuum.py` the pose
pricer ranks candidates by *capture*, which is the pure LP's reduced cost, while 85 % of the
clique LP's dual weight sits on the cut rows the pricer never sees.  Measured: of the 540 poses
that pricer adds per stage, **zero** have positive reduced cost in the clique LP.**

## 1. Step 1 — the same instance on both sides

### 1a. The instance

`clique_continuum.py` writes only the *support* of each stage, not the pose set, so the instance
was rebuilt from what task G left behind: the `r10` support of `runs/cq_A99sw5_support.txt`
(115 orbits, LP mass `11.912723`) together with all 932 anchor cuts of
`runs/cq_A99sw5_cuts.json`, with the coverage rows regenerated by the same exact
arrangement-vertex certifier (`packing_dual.Model.certify`) and the same separator
(`clique_continuum.separate`) run to convergence.  The support contains an optimal basis of the
stage, so this reproduces the stage's LP value; it is not the 4739-orbit pose set (a faithful
replay of that is §1e).

### 1b. Duality: the two implementations agree exactly

`reconcile.py` solves the cover LP from scratch (`min 1.y s.t. A^T y >= 1`, an independent
`linprog` call, not a reading of the packing LP's duals):

| quantity | value | note |
|---|---|---|
| packing LP (max mass, cuts on) | `11.937344` | float LP |
| cover LP (min weight, same instance) | `11.937344` | independent solve |
| `|packing − cover|` | `5.3e-15` | strong duality, as it must be |

So no discrepancy survives on one instance; the disagreement is between two different instances.

### 1c. The credit rules of the two code paths are the same object

`clique_family.contains_np` / `meets_np` (task G: the exact closed unit square of a single pose)
against `anchorclique.member` (task I: a *cell* of the verifier's sweep — `contains` by the
concentric `sigma_k`-square, `meets` by the hexagon `A + [-h,h]^2`).  120 cliques `K(p,A)` built
by `anchorclique.kpa`, 20,000 random poses each, 828,998 memberships:

| cell half-side `h` | G credits | I credits | credited by G, not by I |
|---|---|---|---|
| `1/2` (exact unit square) | 828,998 | 828,998 | **0** (`0.0000 %`) |
| `sigma_k/2`, `N = 2000` | 828,998 | 827,965 | 1,033 (`0.1246 %`) |
| `sigma_k/2`, `N = 6000` | 828,998 | 828,639 | 359 (`0.0433 %`) |

The two implementations agree exactly on the same clique; the cover side is conservative by
`0.12 %` of the credited poses at `N = 2000` and `0.043 %` at `N = 6000`, which is the
`sigma_k`-square being smaller than the unit square and is not remotely the size of the gap.
(`python3 search/reconcile.py xmember JX --n 120 --poses 20000`.)

### 1d. What is actually wrong: the pose pricer of the clique LP

In `clique_continuum.py` the `h > 0` path prices with `reduced_cost(...)`, which *does* subtract
the cut duals.  The `h = 0` path — the only one that passes task G's own calibration, and the one
every headline number was computed on — does this instead:

```python
got = PD.price_sweep(M.m, lib, ax, ay, aw, angs, 6, 0.02, args.threads)   # ax,ay,aw from y only
got = [g for g in got if g[3] < 1.0 - 1e-9]        # capture < 1
got.sort(key=lambda g: g[3])                       # rank by capture
cand = [(g[0], g[1], g[2]) for g in got[:args.cg_want]]
```

`capture` is `sum_{p in S} y_p`, i.e. the *pure* LP's reduced cost `1 − capture`.  The clique
LP's reduced cost is `1 − capture − sum_{K ∋ S} y_K`.  Dropping a non-negative term is harmless
as a *filter* (it can only over-state the reduced cost, so no improving column is missed) and
fatal as a *ranking*: on the dual the LP returns for the clique instance the point rows carry
only `1.85` of the `11.94`, the rest sitting on the cut rows, so the capture of nearly every
admissible pose is `≈ 0` and the ordering is noise.

Measured on the rebuilt instance (`python3 search/reconcile.py escape J1 …`):

| quantity | value |
|---|---|
| dual weight on point rows / on cut rows | `1.850287` / `10.089071` |
| cuts with positive dual | 46 of 1120 |
| the 540 poses task G's pricer adds per stage — capture-only reduced cost `1 − cap` | min `0.9974`, median `1.0000`, max `1.0000` |
| the same 540 poses — **true** reduced cost `1 − cap − Σ y_K` | min `−0.0026`, median `0.0000`, max `0.0000` |
| of those 540, how many improve the clique LP | **0** |
| perturbations of the LP's own support with positive true reduced cost | **1938**, best `+0.344759` |

Task G's own logs carry the fingerprint without any new run: the sweep's reported "best capture"
is `0.64–0.69` in the pure run (`runs/cq_P99sw1.log` — a healthy pricing gap on an unconverged
pure LP) and collapses to `0.0037–0.023` in the anchor run (`runs/cq_A99sw5.log`), because the
point duals no longer cover the container.

**Consequence.**  The eleven-stage "`8.5×` pose refinement" of `CLIQUE_CONTINUUM.md` §2 added
about 5,900 orbits *none of which the clique LP could use*.  The flatness of that ladder
(`11.897 → 11.913`) is not the clique constraint holding the LP down under refinement; it is the
LP being handed columns it must price out.  The stage values are still correct LP values on their
own pose sets — they are just lower bounds on the clique-LP value over a pose set that was never
refined in the direction the clique LP needs.

### 1e. The cover-side reading of exactly the same fact

The optimal cover of the rebuilt instance (`reconcile.py probe`) costs `11.937344` and consists
of **43 point cliques (weight `9.8208`) and 39 anchor cliques (weight `2.1166`)**.  What it
covers:

| pose set | covered weight |
|---|---|
| the LP's own 115 pose orbits (its rows on the cover side) | min `1.000000`, median `1.000000` |
| 300,000 random admissible poses | min `0.500000`, 1 % quantile `0.7352`, median `1.2200` — **12.74 % below 1** |
| 1,944 small perturbations of its own support poses | min `0.652911`, 1 % `0.6854`, median `1.0000` — **45.99 % below 1** |

So `11.937` is the price of covering a list of 115 pose orbits, and the cover it buys fails on
half of the immediate neighbours of those very poses.  This is the same statement as §1d, read on
the cover side: task I's LP, whose rows *are* the verifier's worst poses, is solving a problem
that task G's LP never posed.

### 1f. A second, smaller artefact: the matched pure value

`clique_continuum.py` computes "pure on the same poses" as one `M.solve()` with the cuts removed
**on the row set the clique loop converged**.  Rows are only guaranteed to make the *clique*
solution coverage-feasible; the cuts-off solution puts its mass elsewhere and generally violates
coverage at points that are not rows, so the reported pure value is an **upper** bound on the
pure LP's value on those poses, and the reported gain is an over-estimate.  On the rebuilt
instance the effect is gross: `13.500000` with rows converged for the clique solution only,
`11.972988` once the pure solution's own violated arrangement vertices are added as rows too
(`reconcile.converge(..., pure_too=True)`).  How large it is on task G's own 5,887-row instances
is measured in §3.
